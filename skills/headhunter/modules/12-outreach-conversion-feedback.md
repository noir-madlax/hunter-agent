## Skill 12: 触达后转化追踪与画像反哺 (Outreach Conversion Feedback Loop)

### Purpose

把"Stage 6 之后"（候选人触达 → 响应 → 沟通 → 面试 → 推进 → Offer → 入职）的实际数据**回灌到 Pipeline 的 Stage 1/2 画像里**，让画像随项目推进越来越准。

> 核心信念：第一版画像永远是猜测。真正的画像在前 20 通电话之后才浮出水面。

### When to Use

- Pipeline 已跑完一遍 (Stage 1-6) 并完成首批触达
- 项目跑了 1-2 周，有触达 → 响应 → 沟通的真实数据
- 客户 / 候选人反馈与初始画像出现矛盾
- 项目进展放缓（响应率↓、感兴趣率↓、面试通过率↓）需复盘
- Offer 接受率异常（高位的反 Offer / 低位的速接）需诊断

### Process: 4 步反哺

#### Step 1：埋点 (Tracking Schema)

每个被触达的候选人，记录以下 8 个最小字段：

| 字段 | 含义 | 取值约束 |
|---|---|---|
| `candidateId` | 候选人 ID | 库内 ID 或外部唯一标识 |
| `tier` | 来源分层 | A/MBB/INV/XB/其他（来自 Stage 4 检索分层） |
| `outreachChannel` | 触达渠道 | 微信/电话/LinkedIn/脉脉/邮件 |
| `outreachResult` | 触达结果 | 无响应 / 已读不回 / 回拒 / 愿沟通 / 已沟通 |
| `decisionStage` | 推进阶段 | 触达 / 初聊 / 推荐 / 面试 / Offer / 入职 / 流失 |
| `dropReason` | 流失原因（如有） | 自由文本，但必须从下方 8 类中选主类 |
| `compRealityVsTarget` | 实际期望 vs 预算 | 在预算内 / 略超 / 严重超 / 低于预算 |
| `lifecycleDays` | 触达到当前状态的天数 | 整数 |

#### Step 2：8 类流失原因归类 (Drop Reason Taxonomy)

用归类替代自由文本，便于跨项目对比。

| 类别 | 含义 | 反哺哪一段 Stage |
|---|---|---|
| **D1 画像偏离** | 实际背景与画像不一致（如 title 同名但内容不对） | Stage 1（信号反演重做）|
| **D2 动机不匹配** | 候选人不在求职状态 / 方向不符 | Stage 2 候选人留存层 |
| **D3 薪酬不匹配** | 期望明显超出预算 | Stage 2 + 客户预算复议 |
| **D4 地点/外派不接受** | 拉美/海外/异地不愿去 | Stage 1 跨度暗示重读 |
| **D5 客户公司印象差** | 候选人对客户品牌/老板有顾虑 | Stage 2 雇主预期层 |
| **D6 流程过慢/反 Offer** | 客户决策慢被对手抢走 | Stage 6 next-step + 客户沟通 |
| **D7 文化不匹配** | 多 stakeholder 风格 / 强度不接受 | Stage 2 失败模式 |
| **D8 触达本身失败** | 联系不上 / 无响应（≥3 次尝试） | Stage 3 库的数据质量 |

#### Step 3：反哺信号 (Signals → Persona Updates)

每 5-10 个流失样本触发一次画像复盘：

| 触发条件 | 反哺动作 |
|---|---|
| Tier A 命中率 < 20% 且 D1 占比 ≥ 50% | Stage 1 重做：雇主"成功范本"判定错了 |
| D2 占比 ≥ 40% | Stage 2 + 候选人触达话术：动机筛选问题前置到首聊 |
| D3 平均超预算幅度 ≥ 30% | 回客户预算复议 + Stage 5 Rubric 薪酬维度降权 |
| D4 占比 ≥ 30% | Stage 1 跨度暗示重读：客户是否真要外派？ |
| D5 集中 → 跟某个 stakeholder 名字相关 | 触发对该 stakeholder 的市场口碑研究 |
| D6 ≥ 25% | 不是人的问题，是流程问题 → 客户进度警报 |
| D7 集中在某一类背景（如 MBB） | Stage 2 失败模式预演已验证 → 调整目标公司池 |
| D8 占比 ≥ 50% | Stage 3 体检结论：库的数据质量比预估低 |

#### Step 4：画像 v2 / v3 输出

每次反哺都生成一份 **画像演化日志**，不直接覆盖 v1：

```markdown
## 画像演化：{{项目名}} v{{N}}
### 触发反哺的数据
- 已触达：N，响应：N'，已沟通：N''，推荐：N'''
- 主要流失原因 Top 3：D{{X}} / D{{Y}} / D{{Z}}

### v{{N-1}} → v{{N}} 关键变化
- 改动 1：{{字段}} 从「{{旧值}}」 → 「{{新值}}」  
  依据：{{X 个样本中 Y 个指向...}}
- 改动 2：...

### Stage 1 假设重判
- 假设 a（{{旧假设}}）→ {{保留 / 修正 / 推翻}}
- 假设 b（{{旧假设}}）→ {{保留 / 修正 / 推翻}}

### 下一阶段 sourcing 方向调整
- 加：
- 减：
- 维持：
```

### Guardrails

1. **不允许"画像随情绪改"** —— 每次反哺必须有 ≥ 5 个样本数据支撑
2. **不允许覆盖式更新** —— 画像演化日志必须保留 v1, v2, v3 历史
3. **不允许把"客户决策慢"伪装成"市场没人"** —— D6 高发时必须警报给客户
4. **不泄露候选人流失原因细节给其他候选人** —— 流失原因只对项目内部可见
5. **库的盲区由反哺验证** —— Stage 3 体检结论若被反哺数据推翻（如预估盲区其实有），必须更新

### Anti-patterns

- ❌ 跑了几通电话就大改画像（样本不足）
- ❌ 流失原因写"不合适"这种空话（必须归类到 D1-D8）
- ❌ 反哺只看响应率，不看决策阶段分布
- ❌ 把数据反馈藏起来，只给客户看"漂亮的"漏斗
- ❌ 反哺日志只写"调整了画像"，不写"基于什么数据 + 推翻了哪个 v1 假设"

### Handoff

本模块的输出 **必须回灌 Stage 1 和 Stage 2**：
- 反哺日志 → module 00.5 的"假设清单"（标注被推翻 / 保留）
- 反哺日志 → module 01 的"失败模式预演"（验证 / 修正）
- 反哺日志 → module 03.5 的"库的盲区"（验证 / 修正）
- 反哺日志 → module 10 的 Rubric 权重（按实际流失原因升降权）

> 画像不是写一次的文档。是项目生命周期里持续演化的活体。
